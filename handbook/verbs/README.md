# Verbs

How a dplyr verb is implemented in duckplyr: which verbs get a method, what a generated method does,
when it falls back to dplyr, and how a verb gains support for more of its arguments or is added.
Translating the R functions used inside a verb is [`translations/`](/handbook/translations/README.md)'s.

**Which verbs get a method is computed from dplyr.**
`df_methods` in [`tools/00-funs.R`](/tools/00-funs.R) starts from every S3 method dplyr registers for `data.frame`,
and its filters and flags, each with a comment, decide the rest:
deprecated and lazyeval methods and a few internal generics get nothing,
`skip_impl` marks generics that are tested but not wrapped,
and `always_fallback` marks generics whose method is generated to fall back every time.
A generic dplyr adds appears in the table at the next sync without any change here.

**A generated method tries DuckDB, then forwards to dplyr.**
`R/<verb>.R` defines `<verb>.duckplyr_df()`, whose body has three parts:

* a call to `rel_try()` whose last argument is the relational implementation, ending in `return(out)`;
* the fallback, which calls `check_prudence()` and then the installed dplyr's `<verb>.data.frame()` method;
* after a final `return()`, a copy of that dplyr method's source as of the last sync, under `# dplyr implementation`,
  which never runs and shows what dplyr changed as a diff at the next sync.

Fresh from the generator, the relational part is only a fallback condition,
`"No relational implementation for {.code <verb>()}" = TRUE`;
the implementation replaces it in the committed file, and the patch file keeps it
([`dplyr-alignment/patches/`](/handbook/dplyr-alignment/patches/README.md)).
The verb's help page is hand-written in `R/<verb>-rd.R`.

**`rel_try()` in [`R/relational.R`](/R/relational.R) decides when to fall back.**
Each named argument before the implementation is a drop-out condition, named by the message the user sees:
the first that is `TRUE` falls back, and so does an error raised by the implementation.
`DUCKPLYR_FORCE=TRUE` turns a fallback into an error, `DUCKPLYR_FALLBACK_FORCE=TRUE` falls back every time,
and `DUCKPLYR_FALLBACK_INFO=TRUE` reports each fallback as it happens.
The roxygen lines between the conditions, under `@section Fallbacks:`, document them on the verb's help page,
so a condition and its documentation change together.

**`library(duckplyr)` makes every data frame use these methods.**
`R/overwrite.R`, generated by `tools/07-overwrite.R`, registers each `<verb>.duckplyr_df()` as dplyr's `data.frame` method,
and `R/restore.R` puts dplyr's back; [`R/zzz.R`](/R/zzz.R) calls the first on attach and the second on detach,
except when the package is loaded by devtools.

**Supporting more of a verb's arguments** removes a drop-out condition and implements what it excluded;
the steps are the contributing guide's,
[Support more options for verbs](https://github.com/tidyverse/duckplyr/blob/main/.github/CONTRIBUTING.md#support-more-options-for-verbs).

**Adding a verb** means a new dplyr generic, which the guide asks to discuss first.
Its method file is generated at the next sync, provided the two-pass run keeps it
([`dplyr-alignment/sync/`](/handbook/dplyr-alignment/sync/README.md)), and falls back until it has an implementation;
a generic that should get no method is excluded in `df_methods` with a comment saying why.

**The verbs without a relational implementation are listed for users.**
`tools/80-unsupported.R` scans `R/` for the generated fallback message and writes `R/not-supported.R`,
which is the help page `?unsupported`; the page updates itself when a verb's implementation lands.
